# Qwen3.6-35B-A3B & Qwen3.6-27B for Local VLM Visual Inspection — Deep-Dive Brief (as of July 2026)

**Source-reliability note up front:** Alibaba/Qwen published both as VLMs, but much of the web coverage is AI-generated content-farm material (localaimaster, buildfastwithai, insiderllm, runaihome, promptquorum, various Medium posts) that recycles and sometimes fabricates benchmark numbers. I anchored on the **official Hugging Face model cards** (`Qwen/Qwen3.6-35B-A3B`, `Qwen/Qwen3.6-27B`), the **QwenLM GitHub READMEs**, the **vLLM recipes page**, and the **Qwen3-VL Technical Report (arXiv 2511.21631)**. Treat single-decimal benchmark figures as ±1–2 pts and validate on your own frames. Farm/aggregator claims are flagged where used.

---

## 0. The architectural fact that dominates every deployment decision

Both Qwen3.6 models are **natively-multimodal, early-fusion** VLMs on a **Qwen3-Next-style hybrid linear-attention backbone** (Gated DeltaNet + sparse MoE / dense FFN), **not** standard full attention. From the official cards:

- **35B-A3B:** `10 × (3×(Gated DeltaNet → MoE) → 1×(Gated Attention → MoE))` → **40 layers, only 10 full attention**, 30 GDN linear. Hidden 2048, **256 experts, 8 routed + 1 shared active (~3B active)**. (HF card, 2026-04-16)
- **27B dense:** `16 × (3×(Gated DeltaNet → FFN) → 1×(Gated Attention → FFN))` → **64 layers, 16 full attention**, hidden 5120, dense FFN (all 27B active). (HF card, 2026-04-22)
- Gated Attention = GQA **16 Q / 2 KV heads** → small per-layer KV.

**Consequence:** the growing KV cache lives in only ¼ of layers; the rest carry constant-size recurrent state. For your workload (7–9K vision tokens/frame + shared few-shot image prefix) this means **far smaller KV footprint and cheaper long prefills than any full-attention VLM** (Qwen3-VL-32B, GLM-4.6V), and **prefix-caching the shared image prefix is extremely effective**. This maps almost perfectly onto shared-prefix batch inspection. Loads in vLLM as model type `qwen3_5_moe`.

*Caveat:* one fetched community guide (lastloop-ai) summarized it as "standard attention, no DeltaNet" — contradicts the official cards and every other source; treat as a summarization/language-only-scope error. The GDN hybrid is real.

## 1. Vision capabilities & benchmarks

**Vision stack (inherited/upgraded from Qwen3-VL, arXiv 2511.21631):** dense ViT, **patch 16**, 2×2 merge → **32× spatial compression**, **DeepStack multi-level ViT fusion** for fine detail, native dynamic resolution.

**Image-token math (confirmed for Qwen3.6, HF discussion #36 on the 35B card):** `tokens = h·w/(32×32) + 2 = h·w/1024 + 2` — **identical to Qwen3.5/Qwen3-VL.**
- Your **4464×2160** frame: native 9.64M px → **~9,416 vision tokens**. Default `max_pixels` ~**7.84M** (→ ~7,656 tokens) so native frames get slightly downscaled unless raised; max ~16M px. **For small overlay numbers, keep `max_pixels` near native (~9–10M) — the binding constraint on reading fine digits is the pixel budget, not the model choice.**

Adequate for Korean street text; spot-check your specific overlay font rendering.

## 2. Thinking, structured output, grounding

- **Hybrid thinking:** both default to thinking (`<think>…</think>`); toggle via `enable_thinking=False` / `/no_think`. New "thinking preservation" keeps reasoning across turns (irrelevant for stateless batch — off). **For thousands of constrained-JSON frames, run non-thinking**; reserve thinking for hard re-check passes.
- **Structured output:** standard Qwen tool/JSON; use vLLM **guided decoding (xgrammar/outlines)** to hard-constrain the schema. `--reasoning-parser qwen3`.
- **Grounding/bbox:** native, strong (RefCOCO ~92); outputs **absolute-pixel** boxes (Qwen3-VL convention, not 0–1000 normalized like 2.5-VL). Good fit for boxes over the overlay.

## 3. MTP / speculative decoding

- **MTP is built into the checkpoints** (NEXTN multi-step draft head, Qwen3-Next lineage). vLLM: `--speculative-config '{"method":"mtp","num_speculative_tokens":3}'`. Measured on Blackwell (lastloop-ai): **mean accept length ~3.19, ~73% draft accept, per-position 0.87/0.72/0.60**; n=5 only +4% over n=3 → **use n=3**. Needs `--enable-prefix-caching` + `--enable-chunked-prefill`.
- **Throughput caveat (matters for batch):** MTP cuts single-stream latency but **consumes KV/compute and reduces aggregate throughput under high concurrency** (kaitchup "DFlash vs MTP," 2026; vLLM discuss). **For max-throughput batch, disable MTP** and lean on large batch; enable only for latency-sensitive runs.
- **DFlash speculator** (public checkpoints, both) drafts a block per forward pass and **holds up under concurrency**: **2.29× single-stream / 2.49× at 3 concurrent streams on 35B-A3B FP8** (kaitchup / Allen Kuo Medium, 2026) — better choice if you want speedup *and* concurrency.
- **EAGLE-3 drafts exist** (community `Ex0bit/Qwen3.6-27B-PRISM-EAGLE3`): accept ~2.4 chain, ~3.35 tree but throughput-neutral → chain only. **EAGLE-3 is worse than built-in MTP here; no reason to prefer it.**

## 4. Quantized checkpoints (July 2026) & VRAM math

**Available:**
- **Official FP8** — both (`Qwen/Qwen3.6-27B-FP8`, native FP8 for 35B-A3B). Quality-safe.
- **NVFP4 (Blackwell-native FP4)** — **`unsloth/Qwen3.6-35B-A3B-NVFP4` + an NVIDIA official NVFP4** (knightli guide, 2026-05-31); community 27B NVFP4 (`rdtand/...`, confirmed RTX 5090 / CUDA 13.2 / vLLM 0.20.2). Reportedly **within noise of BF16** (MMMU-Pro/IFBench even slightly up) per unsloth card. **On SM120, NVFP4 is the preferred 4-bit path (native FP4 tensor cores) over AWQ-INT4.**
- **AWQ / GPTQ-Int4** — community 27B AWQ (`QuantTrio/Qwen3.6-27B-AWQ`, `-AWQ-6Bit`, `cyankiwi/...-AWQ-INT4`, "vision preserved," tuned for SGLang/RDNA4); GPTQ-Int4 in family. AWQ = fallback if NVFP4 tooling misbehaves.

**Realistic VRAM per 32GB RTX 5090** (weights + ViT ~1–2GB + hybrid KV for ~7–9.4K vision tokens; hybrid GDN keeps KV small):

| Config | Weights | Fits 1×5090? | Deployment |
|---|---|---|---|
| **35B-A3B NVFP4** | ~19–20GB | **Yes**, ~10GB headroom | **DP=4, 1 replica/GPU** ✅ best |
| 35B-A3B FP8 | ~35GB | No | 2-GPU/replica → 2 replicas across 4 |
| **27B NVFP4/INT4** | ~15–16GB | **Yes**, comfortable | **DP=4, 1 replica/GPU** ✅ |
| 27B FP8 | ~27GB | Tight — only w/ small KV & short outputs; risky at 9.4K vision tokens | prefer 2-GPU, or NVFP4 on 1 |
| 27B BF16 | ~54GB | No | TP=2 → 2 replicas across 4 (quality ceiling) |

(unsloth NVFP4 card claims 32GB-GPU fit for 35B-A3B; lastloop-ai ran FP8 on a 96GB card and notes "on 5090 use INT4/FP4 instead of FP8.")

## 5. vLLM / SGLang maturity on Blackwell SM120

- **Loads as `qwen3_5_moe`** — same path as Qwen3.5 MoE, **already supported**. Recipe lists **min 0.17.0** (0.24.0+ only for NVFP4 on DGX Spark). **Realistically use 0.20.2+ or a cu130 nightly** for stable SM120 + hybrid + FlashInfer + MTP; `vllm/vllm-openai:cu130-nightly` ships SM120 kernels. Confirmed working: **RTX 5090 + CUDA 13.2 + vLLM 0.20.2** (rdtand HF discussion, 2026).
- **FlashInfer** = recommended backend (FP8 KV, better at 128K+); needs the **system CUDA 13 toolkit** or JIT fails on SM120.
- **Hybrid / Mamba-cache gotchas (real, will bite):**
  - GDN layers use a fixed pool of "Mamba cache" blocks; default `--max-num-seqs 1024` exceeds available (~981) → **cap `--max-num-seqs`** (guide used 8–512 by context).
  - **"Prefix Caching (Mamba) experimental in 'align' mode"** (vLLM recipe) — verify shared-prefix caching actually engages for the GDN layers on your version; this is the feature you most depend on.
  - CUDA-graph capture can OOM on hybrid → may need lower `--max-cudagraph-capture-size`.
- **Multimodal specifics:** recipe/guides are language-only-focused and don't document `limit-mm-per-prompt`/`max_pixels` — set yourself (`--limit-mm-per-prompt image=N`, `max_pixels` via mm-processor kwargs / `--hf-overrides`). No SM120-specific *multimodal* bug surfaced, but **the vision path on the hybrid backbone is newer than the text path — regression-test OCR on your frames before committing.**
- **SGLang** also supports it (community AWQ builds target SGLang/RDNA4); vLLM is the more proven Blackwell path today.

## 6. Does the 3B-active MoE degrade fine-detail perception? (key risk question)

No community A/B specifically on small-overlay-number reading surfaced (only farm-level "new SOTA for local vision" claims). But the architecture answers it cleanly:
- **The vision encoder (ViT + DeepStack) is a full dense module — NOT sparsified by the MoE.** Raw perception / OCR *extraction* of a small number or Korean glyph is **encoder-bound and essentially identical across 27B-dense and 35B-A3B** (same ViT lineage, same ~89–90 OCRBench).
- The 3B-active limit bites on **reasoning/aggregation over many regions at once** (cross-referencing BEV + overlay + boxes in one pass, long multi-field JSON). There the **dense 27B (all params active) has more working capacity** than 35B-A3B, and 122B-A10B more still.
- Practical: for "read this number / this box / this label," A3B is fine; for "reason jointly over the whole debug screen and emit a rich verdict," dense 27B is safer. And **for reading small text, `max_pixels` matters far more than 27B-vs-35B-A3B** — do not starve resolution.

## 7. Verdict — where 3.6-27B and 3.6-35B-A3B slot vs the three shortlisted candidates

**(a) Max-throughput batch inspection on 4×5090 DP replicas — Qwen3.6-35B-A3B NVFP4 is the throughput winner, clearly.** It's the only strong candidate that (i) fits **one 5090 per replica → DP=4 (four independent replicas)** while your shortlist is all TP=4-over-PCIe single-replica or dense (122B-A10B AWQ TP=4, GLM-4.6V AWQ TP=4, Qwen3-VL-32B BF16 TP=4 — all pay PCIe all-reduce with no NVLink, one replica), (ii) runs **3B active compute**, and (iii) exploits **hybrid-GDN small-KV + shared-image-prefix caching** a full-attention VLM cannot. Expect it to beat all three on frames/sec by a wide margin. **3.6-27B dense NVFP4** also does DP=4 but with 27B active compute — lower throughput than A3B, higher single-frame reliability; slots **above the three shortlisted on throughput, below 35B-A3B.**

**(b) Quality ceiling — 3.5-122B-A10B (AWQ, TP=4) stays the ceiling**, but only marginally and only on MMMU-style reasoning; on the **document/OCR/grounding axes that define this workload it's a near-tie with 3.6-27B** (OmniDocBench 90.8 vs ~90; both ~89 OCRBench, ~92 RefCOCO). **Qwen3-VL-32B** is a solid pure-vision baseline but 3.6 matches/exceeds it on docs while adding reasoning + hybrid efficiency, and as a full-attention dense model is the weakest throughput fit. **GLM-4.6V** is competitive on grounding but doesn't lead Qwen on overlay-text/doc-OCR. **3.6-35B-A3B sits just a hair below 3.6-27B** on the hardest joint-reasoning frames, essentially tied on perception/OCR.

**Recommended serving configs:**
- **Primary / throughput:** `4 × [Qwen3.6-35B-A3B-NVFP4, 1 GPU each, DP]`. vLLM 0.20.2+ (cu130), FlashInfer, `--kv-cache-dtype fp8_e4m3`, `--enable-prefix-caching` + `--enable-chunked-prefill` (cache the shared few-shot image prefix), `--reasoning-parser qwen3` with **thinking OFF**, guided-JSON (xgrammar), `max_pixels ≈ 9–10M` (don't starve small-number resolution), **`--max-num-seqs` capped** (start ~16–32; watch Mamba-cache blocks), **MTP OFF for max batch** (or DFlash if you want speedup with concurrency). Front with a health-aware round-robin router across the 4 replicas.
- **Quality-balanced:** `4 × [Qwen3.6-27B-NVFP4, 1 GPU each, DP]` — best quality-per-throughput; same flags. Use if fine multi-panel reasoning shows A3B misses.
- **Max fidelity (fewer replicas):** `2 × [Qwen3.6-27B-BF16, TP=2]`, or keep one `Qwen3.5-122B-A10B-AWQ TP=4` replica as a **second-pass re-checker** for low-confidence frames.

**Bottom line:** the hybrid-GDN + native-multimodal design makes **3.6-35B-A3B NVFP4 DP=4** the standout throughput pick for this shared-prefix batch workload, with **3.6-27B** as the drop-in quality upgrade that still runs one-GPU-per-replica — both dominate the TP=4 shortlist on throughput and give up almost nothing on OCR/grounding quality. Validate NVFP4 OCR accuracy and Mamba prefix-caching on your own 4464×2160 frames before locking in; those two are the only places where the newer hybrid-VLM code paths (and content-farm-sourced numbers) carry real uncertainty.
