# Multi-GPU LLM/VLM Inference on RTX 5090 (Blackwell consumer, sm_120) — Field Report, July 2026

## 1. Software support status (mid-2026)

**PyTorch / CUDA**
- sm_120 has been officially supported since **PyTorch 2.7.0 (Apr 2025)** with cu128 wheels (cuDNN/NCCL/CUTLASS upgraded for Blackwell) (PyTorch 2.7 release blog, Apr 2025). **PyTorch 2.10 shipped Jan 21, 2026** (Phoronix, Jan 2026); per PyTorch dev-discuss, **CUDA 13.0 became the stable PyPI wheel variant with release 2.11**, and **release 2.12 introduces CUDA 13.2 and deprecates 12.8** (dev-discuss.pytorch.org, 2026). Practical rule: anything ≥2.7 cu128 runs on a 5090; use ≥2.9/2.10 for a modern stack. The 2025-era "no kernel image for sm_120" pain is over for PyTorch itself.
- Note sm_120 ≠ "Blackwell" in general: datacenter Blackwell is SM100/SM110; many "Blackwell" kernels target those, not SM120 (elevata.io, Jun 3, 2026).

**vLLM** — the most mature engine for SM120:
- 2025 history: TP on sm_120 hung at NCCL init in 0.9.x docker (vllm#21491, Jul 2025, closed stale; vllm#14628 Mar 2025), and pre-0.10 required source builds against torch nightly (`TORCH_CUDA_ARCH_LIST="12.0"`, `VLLM_FLASH_ATTN_VERSION=2`) (discuss.vllm.ai "working RTX5090 setup", Sep 2025).
- Current: **vLLM ≥ v0.17 ships a dedicated SM120 FP8 GEMM path** (Runpod RTX 5090 guide, 2026); merged work includes swapAB SM120 CUTLASS blockwise-FP8 GEMM (PR #38325), **FlashInfer b12x MoE + NVFP4 GEMM for SM120/121** (PR #40082), per-tensor FP8 CUTLASS on SM121. CUDA graphs on sm_120 confirmed working (vllm#37242, 2026).
- Remaining gotchas: stock images may still need explicit SM120 pinning for FlashInfer (`FLASHINFER_CUDA_ARCH_LIST=12.0f`, `FLASHINFER_FORCE_SM=120f`) (elevata.io, Jun 2026); expect the startup warning "**custom allreduce is disabled because your platform lacks GPU P2P capability**" on multi-5090 — that is normal and permanent on stock drivers (vLLM forums, 2025-2026). Many kernels (esp. fused MoE) lack tuned configs for sm_120 and fall back to generic/untuned paths; people ship hand-tuned MoE JSON configs (smcleod.net, Feb 25, 2026).

**SGLang** — works but clearly second-tier on SM120: sgl-kernel Blackwell compat issues (sglang#9542), **blockwise FP8 not supported on SM120** (sglang#9233), auto-selected `trtllm_mha` backend then raises ValueError "only supported on SM100" on 5090 (sglang#14814), GPT-OSS Triton-MoE PTXAS crashes on sm_120a leaving no valid attention+MoE combo for some models (sglang#9140). Verify your exact model works before committing.

**TensorRT-LLM** — GeForce Blackwell support exists but is the roughest: FP4 GEMM check relaxed to allow GeForce Blackwell around 0.20.0rc3 (TRT-LLM#5018); RTX 50 support originally "WSL, limited models" in the official matrix; SM120 kernel gaps persist and NVFP4 on 32GB 5090 hit managed-weights/type-check bugs in v1.2.0rc4 (TRT-LLM#9503), with community patch repos to run 30B MoE NVFP4 on a 5090 (JohnTDI-cpu/trtllm-nvfp4-blackwell-fix, 2026; TRT-LLM discussion #8334). Multi-GPU TRT-LLM on GeForce is not a supported/trodden path — do not plan around it.

**FlashAttention** — official Dao-AILab flash-attn still does **not** support SM120 (issues #1665, #1987 — no committed date); FA3 is Hopper-tuned; FA4 targets SM80/90/100 but not SM120. Root cause: SM120 lacks WGMMA (uses SM80-era MMA) and has only ~99-101KB shared memory vs 227KB on SM100, so Hopper/B200 kernels don't port (sorryhyun blog "FA4 on SM120", 2026). Community forks/wheels exist (roy86/flash-attention_sm120; SecondNatureComputing flash-attn-4-sm120 bundling six upstream PRs) with caveats like **head_dim ≤ 128 only** — relevant for some VLM vision towers. In practice vLLM on 5090 uses FlashInfer, FA2, or Triton attention, not FA3.

**xformers** — PyPI wheels only built through sm_89 as of early 2026; must compile from source for sm_120, and it's a known "dependency trap" (pip pulling xformers can downgrade your torch). Standard advice: skip xformers, use SDPA/FlashInfer (lilting.ch ComfyUI-Blackwell writeup, 2026).

## 2. Interconnect: no NVLink, no P2P — plan around it

- **NVIDIA officially confirmed P2P is disabled on RTX 50 GeForce**: "RTX 50-series are GeForce GPU series, and P2P is not supported for GPU↔GPU" (NVIDIA staff, developer forums thread #326776, Mar 2025). Same product segmentation as the 4090.
- **Early NCCL crashed outright on 2x 5090** (`unhandled cuda error` in all_reduce_perf; NCCL#1637 Mar 2025, nccl-tests#287) because it tried P2P paths. Fixed in updated NCCL (≥2.26.x era): NCCL now **falls back to shared-memory transport staged through host RAM**. So TP works, but every all-reduce is GPU→host→GPU over PCIe.
- **2026 tinygrad-equivalent exists**: `aikitoria/open-gpu-kernel-modules` (descendant of the tinygrad 4090 P2P hack) **explicitly supports RTX 5090**, current branch `610.43.03-p2p` (earlier 590.48.01). It force-enables BAR1 P2P; requires **ReBAR/large BAR, `iommu=pt` (passthrough, not translating), and ACS disabled**; measured **~111 GB/s bidirectional between two 5090s** with sub-µs latency (repo README, 2026). smcleod.net (Feb 25, 2026) measured **10–30% vLLM throughput gain** from P2P on consumer cards and notes you must also patch vLLM's P2P capability check in `vllm/platforms/cuda.py` (pynvml hardcodes consumer-card rejection). Unofficial, unsupported, and a real security tradeoff (`iommu=pt` + ACS off = no DMA isolation) — viable for a dedicated inference box, not for multi-tenant.
- **Env vars that matter on stock drivers**: `NCCL_P2P_DISABLE=1` (prevents NCCL probing P2P paths that then fail; harmless since P2P is off anyway), keep `NCCL_SHM_DISABLE=0` (SHM is your fast path), `NCCL_CUMEM_ENABLE=0` (vLLM sets this itself; external processes joining its NCCL groups must match), `CUDA_DEVICE_ORDER=PCI_BUS_ID` for stable device numbering, `NCCL_DEBUG=TRACE` + `CUDA_LAUNCH_BLOCKING=1` for hang debugging (vLLM troubleshooting docs). TP hangs still occasionally recur on Blackwell + CUDA 13.0 + NCCL 2.27.7 (vllm#33041, on dual RTX PRO 6000; late 2025) — pin known-good NCCL versions.
- **Measured multi-5090 scaling** (all PCIe 5.0 x16, no P2P):
  - CloudRift (Sep 23, 2025), Qwen3-Coder-30B, vLLM, concurrency 200: **a single RTX PRO 6000 beat 4x 5090 with TP=4** (and 4x 4090). TP over PCIe burns most of the aggregate compute on communication for small/medium models. Also: upgrading driver 570.86 → 575.57 gave "significant gains in all vLLM benchmarks" on 5090.
  - CloudRift (Oct 9, 2025): best absolute throughput came from **replica parallelism / pipeline parallelism, not TP**: 4x 5090 = **12,744 tok/s** on 30B-AWQ (4 replicas + NGINX), 2x 5090 = 1,230 tok/s on Llama-3.3-70B-AWQ (PP=2), 4x 5090 = 4,622 tok/s on GLM-4.5-Air-AWQ (~96GB, PP=4). Their explicit conclusion: use PP for models that don't fit on one card, replicas for those that do; TP costs VRAM and PCIe overhead.
- **Bottom line for your 4-GPU VLM plan**: TP=4 will function (post-2025 NCCL fixes) but the per-layer all-reduce through host memory hits decode latency hard; the community consensus for consumer Blackwell is **PP (or TP=2 x PP=2) for capacity, replicas for throughput**, TP=4 only if single-request latency demands it and the model can't be served otherwise. If you control the box and accept the security tradeoff, the patched P2P driver claws back 10-30%.

## 3. Precision (5th-gen tensor cores: FP8 + NVFP4)

- **FP8**: the workhorse. vLLM ≥0.17 has SM120-specific FP8 GEMMs (per-tensor and blockwise-CUTLASS) (Runpod 2026; vLLM PRs); FP8 KV cache (`--kv-cache-dtype fp8`) is standard on 32GB cards. SGLang's SM120 blockwise-FP8 was still a gap (sglang#9233). Mid-2026 consensus: **FP8 is the safest production precision** (quantizelab GPU guide, 2026).
- **NVFP4**: hardware-native on Blackwell only. Works today on SM120 via **vLLM + ModelOpt NVFP4 checkpoints + FlashInfer b12x** (`--quantization modelopt_fp4`, FP8 KV cache, `FLASHINFER_FORCE_SM=120f`), validated in a June 3, 2026 production writeup (elevata.io) — which warns stock images are insufficient and that speculative-decoding config leakage into the drafter causes shape/assert failures. TRT-LLM NVFP4 on 5090 works with patches (see §1). Quality: DeepSeek-R1 MMLU dropped only 90.8→90.7 FP8→NVFP4 (Spheron NVFP4-vs-MXFP4 guide, 2026). Real-world LLM gains are mostly **capacity** (fitting bigger models in 32GB) and prefill/compute-bound throughput; decode remains bandwidth-bound so format speedup there is modest. The headline "3x FP4" numbers come from image-gen/TensorRT (NVIDIA blog; ComfyUI NVFP4 guide, 2026), not LLM decode. Kernel coverage for FP4 attention/MoE on SM120 is still community-driven (e.g., FP4 fused attention kernel blog, florianmattana.com, 2026).

## 4. Ops for an 8x 5090 box

- **Power**: 575W TDP x8 = 4.6kW GPU alone; measured 8-GPU systems exceed **4,000W wall** (Simcentric, Apr 2026). Single-card transients hit **901W for <1ms** (TechPowerUp, 2025) — size PSUs/circuits with headroom, and watch 12V-2x6 connectors: wires at the PSU end measured **150°C** under sustained 575W in testing (Simcentric/der8auer-derived, 2026).
- **Power capping**: `nvidia-smi -pl 450` (or 400) is standard practice for dense rigs. LLM decode is memory-bandwidth-bound, so capping 575→450W typically costs single-digit-to-~15% decode throughput while cutting ~22% power; compute-bound prefill/batch loses proportionally more (5090 perf scales ~linearly with TDP in compute workloads — Notebookcheck 2025; analogous 4090 result: 90% tuning perf at 55% power, dev.to maximsaplin). Test your own workload; no authoritative 5090-LLM capping curve was published.
- **Cooling**: air-cooled 8x runs 73-75°C with throttling events (85% sustained util); liquid runs 58-60°C, no throttling, 97% util, ~400W lower total draw (Simcentric, Apr 2026). Blower/watercooled variants or a purpose server chassis (e.g., ASUS ESC8000A-class with 8x PCIe 5.0 x16 on dual EPYC — a16z build, Apr 2025) strongly preferred over risers; riser/OCuLink links correlate with Xid 79 bus drops (NVIDIA forums, 2025-26).
- **MIG: NO** on GeForce including 5090 (NVIDIA MIG docs; Spheron GPU-sharing guide). **MPS: YES** (Volta+ full support, per-client address spaces) — useful for packing replicas. **ECC: NO** user-visible/configurable ECC on GeForce (pro cards only).
- **Driver stability**: must use **open kernel modules** (`-open`) for Blackwell. 2025-26 threads document Xid 79 "fell off the bus"/GSP heartbeat timeouts under sustained CUDA load (one confirmed trigger: AMD AGESA PI-1.3.0.0 BIOS — rollback to 1.2.0.3f fixed it), plus Xid 13/109/119 reports (NVIDIA dev forums, 2025-2026). Driver 575.57+ materially faster than 570.x for vLLM on 5090 (CloudRift, Sep 2025); 595.71.05 (Apr 2026) is a current stable branch. Pin and burn-in test.
- **BIOS/kernel**: enable Above-4G Decoding + **Resizable BAR** (mandatory for the P2P patch, and early Linux 5090 bring-up had ReBAR-related detection failures); set `iommu=pt` (or disable IOMMU) and **disable ACS** so GPU↔GPU PCIe traffic isn't routed through the root complex — required for patched P2P, and reduces NCCL SHM-path overhead generally (aikitoria README; NCCL guidance).

## 5. Alternative: RTX PRO 6000 Blackwell 96GB (brief)

Same GB202 silicon class, 96GB GDDR7 at the same ~1.79 TB/s bandwidth, 600W, and — unlike GeForce — **P2P supported, ECC, MIG**. CloudRift (Sep 2025) measured **one PRO 6000 outperforming four TP=4 5090s** on a 30B model; ~1.8x per-GPU throughput on 30B+ concurrent serving vs 5090 (Spheron comparison, 2026). Street price ~$8,000–9,400 (Jun 2026). For a single VLM needing >32GB, one PRO 6000 (or two with TP=2 + working P2P) eliminates the entire PCIe all-reduce problem, at ~1/4 the power of four 5090s — the standard recommendation for exactly this niche when budget allows; the 8x 5090 box then serves replicas/smaller models where it excels.

## Practical takeaway for "one VLM on 4x 5090"

1. Stack: Linux + open driver ≥575 (prefer 590/595 era), PyTorch ≥2.9 cu128/cu130, vLLM ≥0.17 official wheels; FlashInfer attention backend; avoid xformers and official flash-attn; verify SGLang model-by-model.
2. Expect no P2P; export `NCCL_P2P_DISABLE=1`, `CUDA_DEVICE_ORDER=PCI_BUS_ID`, leave SHM on; accept the "custom allreduce disabled" warning.
3. Prefer PP=4 or TP=2xPP=2 over TP=4 unless latency forces TP; if the VLM fits in 32GB at FP8/NVFP4, run 4 replicas instead — it's the measured-best configuration on this hardware.
4. Cap at 450W/card, liquid or server-grade airflow, watch 12V-2x6 connectors, burn-in for Xid 79.
