# VLM-Based Automated Visual Inspection Agent for ADAS Debug Visualizations + Inference-Optimization Experiment Menu — Best Practices, Mid-2026

## 0. Model & Hardware Baseline (context for everything below)

- **Best open VLM family for this task (mid-2026):** Qwen3-VL — dense 2B/4B/8B/32B + MoE 30B-A3B and 235B-A22B (GitHub QwenLM/Qwen3-VL; Wikipedia Qwen, releases Oct 2025). Qwen3-VL-30B-A3B (30.5B total / 3.3B active, 256K ctx) is the sweet spot for quality-per-FLOP and still competitive with commercial frontier models on document/OCR/GUI tasks (Codersera deployment guide, 2026; InsiderLLM "Best Qwen Models Ranked," mid-2026). Requires vLLM ≥ 0.11; Korean text OCR is a Qwen-VL strength (32-language OCR incl. Korean, Qwen3-VL README).
- **4x RTX 5090 realities:** 32 GB each, no NVLink → PCIe-only interconnect; TP across 4 GPUs is bottlenecked, and community benchmarks show **4 independent replicas (data parallel) beat TP=4** for throughput (CloudRift RTX 4090/5090/PRO 6000 benchmark, 2026: 1x5090 = 4,570 tok/s on Qwen3-Coder-30B; 4x = 12,744 tok/s via replicas). Reserve TP=2/TP=4 only for models that don't fit in 32 GB (e.g., Qwen3-VL-32B BF16 ≈ 66 GB weights → TP=4 or quantize).
- **SM120 (consumer Blackwell) caveat:** FP8 is solid; **NVFP4 on SM120 is still rough** — kernel/backend gaps and stability failures reported through early 2026 (vLLM issues #31085, #33416, #35065; FlashInfer #2577; elevata.io SM120 NVFP4 write-up, 2026). Treat NVFP4 as a late-stage experiment, not a default.

## 1. Task Design: VLM-as-Judge for Structured Visual Inspection

### 1.1 Rubric + checklist decomposition (consensus pattern)
- 2024–2026 research consensus: **rubrics improve judge reliability when explicit, criterion-separated, and calibrated**; pass the rubric as structured criterion JSON in the prompt (EmergentMind "VLM-as-a-Judge Evaluation Protocol," 2026; Adnan Masood rubric-eval survey, Medium 2025).
- **Checklist decomposition beats one mega-prompt** for multi-aspect inspection: ask one question per defect class (missed detection? FP boxes? box alignment? lane fit? numeric plausibility? camera↔BEV consistency?) rather than a single "find all problems" prompt. Decomposition prompting literature and training-free VQA-decomposition agents show each independently-answered sub-question is more reliable and more debuggable (Learn Prompting decomposition docs; "Analyzing Modular Approaches for Visual Question Decomposition," arXiv 2311.06411; AnomalyAgent, arXiv 2605.30140).
- Practical compromise for batch cost: **one request per image with a sectioned rubric prompt producing one JSON object with per-check fields** (each field = one checklist item with its own verdict + evidence). Escalate to per-question decomposed calls only for frames the single-pass flags as borderline. This "cheap pass → expensive pass" triage is the standard 2026 pattern for thousands-of-frames batch QA (Label Your Data "LLM as a Judge: A 2026 Guide").
- **Single-shot vs multi-turn:** single-shot per image for batch mode (multi-turn destroys prefix-cache hit rates and adds latency). Multi-turn ("look again at region X") is worth it only in the interactive QA mode or the escalation pass. Active-perception/zoom loops (ZoomEarth, arXiv 2511.12267) show iterative crop-and-zoom improves ultra-high-res accuracy but at 3–10x request cost.
- **Self-consistency voting:** sample N=3–5 verdicts at temperature ~0.6–0.8 and majority-vote per defect class; measurably raises judge accuracy and reduces run-to-run variance ("Rating Roulette: Self-Inconsistency in LLM-as-a-Judge," arXiv 2510.27106; ZeroEntropy self-consistency notes, 2026). Use it (a) during eval-set calibration and (b) on escalated frames only — 3–5x cost is too high for the full batch. Note judges are measurably self-inconsistent across runs, so lock seeds/temperature for regression comparability.
- Domain precedent: **BetterCheck (IEEE ITSC 2025, arXiv 2507.17722)** evaluated GPT-4o/LLaVA/MiniCPM-V as safeguards on Waymo data — VLMs show strong fine-detail understanding of traffic scenes but hallucinate agents (FPs) and miss VRUs (FNs), so a per-defect-class rubric + guardrail verdicts (not free-form description) is required. Broader survey confirms VLM hallucination is the key risk when outputs feed downstream triage (Foundation Models for AD survey, ScienceDirect 2026).

### 1.2 Handling 4464×2160 images: token math, resize limits, tiling
- **Qwen3-VL token math:** SigLIP2 encoder, 16px patches, 2×2 merge → **tokens ≈ H×W/1024** (896×896 = 784 tokens; Qwen3-VL Technical Report, arXiv 2511.21631; HF Qwen discussion #36). Your full frame at native res: 4464×2160 ≈ 9.64 MP → **~9,400 visual tokens/image** if uncapped.
- **Resize caps:** HF/vLLM `mm_processor_kwargs` `max_pixels` controls this. Architectural ceiling ≈ 12.85 MP; recommended working defaults ≈ 1.0–2.6 MP (mlx-vlm issue #1175 documents that the 12.8 MP config value is a ceiling, not a recommendation, and over-res can *hurt* grounding). At `max_pixels = 1,003,520` your frame becomes ~980 tokens; at ~2.6 MP ≈ 2,560 tokens. **Token cost ladder to test: ~1 MP (~1K tok) / ~2.6 MP (~2.5K tok) / ~5 MP (~5K tok) / native (~9.4K tok).** Small on-image text (distances/velocities, Korean street text) is the constraint that pushes you up the ladder.
- **Panel-split strategy (recommended):** crop the debug screenshot **deterministically in preprocessing** (panel layout is fixed and known — don't make the VLM find panels): (1) front-camera panel, (2) BEV panel, (3) optionally 2–3 zoomed crops of the camera panel for small-box/numeric-overlay checks. Inspect each with its own checklist, then run a **cheap text-only cross-check pass** comparing the two panels' extracted object lists (object counts, positions, TL states) — cross-modal consistency as JSON-vs-JSON comparison is far more reliable than asking one prompt to compare two sub-images. Tiling research supports this: tiles preserve local detail that global downsampling destroys, boosting OCR/doc-QA ("Image Tiling for High-Resolution Reasoning," arXiv 2512.11167; ScreenSpot-Pro shows stock VLMs degrade badly on pro-resolution screens, arXiv 2504.07981).
- **Overlap:** if you must tile the camera panel into a grid, use modest overlap (~5–10%) so boxes on tile boundaries aren't split — but note one 2025 study found overlapping tiles can slightly *underperform* non-overlapping (−0.8%), so dedupe flags across overlapping regions (arXiv 2512.11167). Panel-aligned splits avoid the issue entirely.
- **Task-aware resolution:** resolution requirements differ per check — box-alignment and numeric-overlay reading need high res; "is a whole car missed" works at 1 MP. Task-aware resolution selection is an active 2025–26 line (arXiv 2510.09822); operationally: run the cheap 1 MP full-frame pass for gross checks + high-res crops only for fine checks.

### 1.3 Few-shot with exemplar defect images
- Qwen3-VL + vLLM support **multi-image interleaved prompts**; raise `--limit-mm-per-prompt '{"image": N}'`. Pattern: system prompt + 2–4 exemplar images (one clean frame, one missed-detection, one misaligned-box, one BEV-inconsistency) each with its gold JSON verdict, then the query image. Few-shot exemplars measurably help VLM information-extraction tasks (CM1 few-shot VLM extraction dataset, arXiv 2505.04214).
- Keep the exemplar block **byte-identical across all requests** — vLLM hashes image inputs, so identical exemplar images produce prefix-cache + encoder-cache hits across thousands of requests (see §5.2). Budget: 4 exemplars × ~1K tokens each = ~4K prefix tokens, cached once per replica.

## 2. Structured Output (vLLM, 2026)

- **API status:** legacy `guided_json`/`guided_regex` were **deprecated in v0.12.0 and removed**; current API is `structured_outputs={...}` / `StructuredOutputsParams` inside `SamplingParams` for offline `LLM.generate`, and `response_format` / `structured_outputs` extra-body on the OpenAI-compatible server. Backends: **xgrammar (default via "auto"), guidance, outlines**; select with `--structured-outputs-config.backend` (vLLM Structured Outputs docs, latest 2026).
- **xgrammar** is the fastest for most JSON schemas due to JIT-compiled + cached grammars; it's the default across vLLM/SGLang/TensorRT-LLM in 2026 (SqueezeBits guided-decoding benchmark blog; Red Hat Developer structured-outputs article, Jun 2025). Grammar compilation is amortized — with one shared schema across thousands of requests the overhead is near-zero after warmup.
- **Schema design for inspection verdicts:**
  - Flat-ish schema, one object per checklist item: `{"check": enum, "verdict": enum["pass","fail","uncertain"], "severity": enum, "evidence": str, "bbox_region": str|null, "confidence": number}`. Use **enums everywhere possible** (constrained decoding turns classification into forced choice — highest reliability).
  - Put a short free-text `evidence`/`reasoning` field **before** the `verdict` field in property order so the model reasons before committing (order matters with autoregressive constrained decoding — widely-repeated 2025/26 practitioner guidance; Collin Wilkins "LLM Structured Outputs: Schema Validation for Real Pipelines," 2026).
  - Include `"uncertain"` as an allowed verdict — constrained decoding cannot refuse, so give it an escape hatch or you'll get confident garbage.
  - Avoid deeply nested/recursive schemas, `oneOf` unions, and unbounded arrays (xgrammar handles them but slower and models track them worse). Cap array lengths.
  - Pydantic model → `model_json_schema()` → pass to vLLM; parse+validate on the way back and route validation failures to a retry queue (rare with xgrammar but non-zero).
  - Reasoning models: if you use a -Thinking variant, structured outputs apply after reasoning by default; `--structured-outputs-config.enable_in_reasoning` exists but avoid it (vLLM docs 2026).

## 3. Evaluation of the Inspection Agent

- **Ground-truth set:** hand-label 300–1,000 frames with per-defect-class binary/severity labels (same taxonomy as the JSON schema). Stratify: normal frames (majority), each defect class, hard negatives (visually odd but correct), day/night/rain, dense scenes. Use ≥2 human labelers on an overlap subset; compute **inter-annotator Cohen's κ first** (or Krippendorff's α for 3+) — the judge can't beat label noise (arXiv 2606.00093 "Agreement Metrics for LLM-as-Judge Evaluation," 2026).
- **Metrics:** per-defect-class **precision/recall/F1** (recall on missed-detection class is your safety-critical number; precision drives reviewer trust), plus **judge-vs-human Cohen's κ**. 2026 production bar: **κ > 0.6 acceptable, > 0.8 strong** (FutureAGI "LLM-as-a-Judge in 2026"; Judge's Verdict, OpenReview 2025). Published reference points: GPT-4o-class judges hit κ ≈ 0.72–0.83 vs humans on visual tasks. Also track flag-rate drift over time as a canary.
- **Regression harness:** the standard 2026 two-tool stack is a lightweight CI runner (**promptfoo** or **DeepEval** — both support image inputs, JSON assertions, threshold gates in CI) + a platform for human annotation/trace review (**Braintrust** or **LangSmith**; both added first-class multimodal + human-review queues) (Inference.net "LLM Evaluation Tools Comparison," 2026; Braintrust HITL platforms article, 2026). For a local/air-gapped setup, promptfoo is fully self-hostable and diffs eval runs across prompt versions.
- **Prompt versioning:** store prompts + rubric JSON + schema in git (they are code); tag every batch-run output with `{prompt_sha, model, quantization, max_pixels, sampling params}`. Judge self-inconsistency across runs is documented (Rating Roulette, arXiv 2510.27106) — pin temperature (0 or fixed-seed voting) for regression comparability, and re-run the frozen eval set on every prompt/model/quant change.

## 4. Fine-Tuning Path (if zero-shot/few-shot insufficient)

- **Frameworks (2026):** **ms-swift** (ModelScope) — broadest MLLM coverage (300+ MLLMs incl. all Qwen3-VL variants; CPT/SFT/DPO/GRPO; official Qwen-recommended path, qwen.readthedocs.io); **LLaMA-Factory** — Qwen3-VL LoRA/QLoRA at 2–8 bit, YAML-driven, easiest on-ramp; **TRL** (SFTTrainer VLM support, docs/training_vlm_sft.md) — most flexible, most code. **Unsloth** for fastest single-GPU LoRA. All four actively maintained mid-2026.
- **VRAM on 32 GB RTX 5090s:** Qwen3-VL-8B LoRA (bf16, grad-ckpt, ~4K seq) ≈ 22 GB → fits one 5090 (ms-swift docs via Qwen; Spheron VRAM sizing guide, 2026) — but multimodal SFT VRAM scales with image resolution, so cap training `max_pixels` (~1 MP) or you'll OOM. Qwen3-VL-32B LoRA needs QLoRA (4-bit base) on a single 5090, or LoRA sharded across 2–4 GPUs (DeepSpeed ZeRO-2/3 via ms-swift/LLaMA-Factory — works over PCIe, training tolerates the interconnect better than TP inference). 30B-A3B MoE LoRA: feasible with 4-bit base + rank ≤ 32 on 4x5090 with ZeRO-3 (Medium, Shaaf Salman Qwen3-VL-30B-A3B LoRA guide, 2026).
- **Dataset size rules of thumb:** noticeable gains from **100–500 curated examples** for a narrow rubric-following task; **~1,000/task is the commonly cited floor** for robust generalization; 500→5,000 is the standard scaling study range (dialzara small-data guide; arXiv 2511.00130 SFT/LoRA/ICL data-scarcity comparison; Meta "How to fine-tune: focus on effective datasets"). For inspection-style SFT: train on (image crops → gold JSON verdict) pairs harvested from your human-labeled eval overflow + hard frames the zero-shot agent got wrong; keep the eval set strictly held out. Prioritize label quality and defect-class balance over volume; oversample rare defect classes.
- **Sequencing:** exhaust prompt/rubric/few-shot/resolution tuning first — fine-tuning resets your quantization + Eagle3 draft compatibility story (a LoRA-merged model no longer matches published NVFP4/Eagle3 artifacts; you'd re-quantize with llm-compressor and lose off-the-shelf drafts).

## 5. Inference-Optimization Experiment Roadmap (ordered, quick wins first)

**Metrics to track throughout** (vLLM `vllm bench serve` / benchmark suite): TTFT, TPOT/ITL, E2E latency, **images/hour** (the business metric), tokens/s/GPU, GPU-cache-utilization %, prefix-cache hit rate, VRAM headroom, and per-defect-class F1 on the frozen eval set (quality gate: every optimization step must hold κ/F1 within an agreed delta, e.g., ≤1 pt).

**Phase 0 — Baseline (day 1).** Qwen3-VL-30B-A3B-Instruct (or 8B) BF16, 1 replica/GPU where it fits; run the frozen eval set + `vllm bench` to record baseline TTFT/TPOT/images-per-hour/accuracy. All later steps are diffs against this.

**Phase 1 — Free/cheap wins (week 1).**
1. **Resolution ladder (`max_pixels`)** — biggest single lever: visual tokens scale linearly with pixels (H×W/1024). Dropping native 9.4K → 2.5K tokens/image is ~4x less prefill work with typically minor accuracy loss if you pair with panel crops. Find the knee on your eval set.
2. **Prefix + processor + encoder caching** — enabled by default in vLLM V1; identical system-prompt + few-shot-exemplar image prefix across thousands of requests gives KV-cache hits (image inputs hashed), and the multimodal processor cache + encoder cache skip re-encoding repeated exemplar images (vLLM Automatic Prefix Caching + MM Processing docs, 2026). Verify hit rate in logs; keep exemplar bytes identical. Note past correctness bugs with MM prefix caching under high concurrency (vLLM issue #20261) — spot-check outputs at your target concurrency on your pinned version.
3. **Offline batch mode + scheduler tuning** — use offline `LLM.generate`/`LLM.chat` (offline default `max_num_batched_tokens` = 16,384 vs 8,192 online); sweep `max_num_batched_tokens` 8K–64K and `max_num_seqs` (gains plateau ~50) (vLLM Optimization & Tuning docs; AMD vLLM V1 tuning guide, 2026). **Chunked prefill is on by default in V1** — with ~1–2.5K-token image prefills mixed into batches it keeps decode steady; mostly leave alone, tune via `max_num_batched_tokens`.
4. **DP over TP** — 4 independent replicas (or `--data-parallel-size 4`) instead of TP=4: no NVLink means TP pays PCIe tax every layer; replica parallelism scaled ~2.8x on 4x5090 in public benchmarks (CloudRift 2026). Shard the frame list across replicas with a simple work queue.

**Phase 2 — Quantization ladder (weeks 2–3).** Run eval-set quality gate at each rung.
5. **FP8 (W8A8)** — native on Blackwell; use official `-FP8` checkpoints or llm-compressor. Expected: near-lossless quality for VLMs, ~1.5–2x prefill throughput, halves weight VRAM (frees KV cache → bigger batches). The default second rung in 2026 and likely your production point.
6. **FP8 KV cache** (`--kv-cache-dtype fp8`) — per-token KV cost drops to ~54% of BF16; benefit is decode-side and grows with context; break-even ~7K tokens on Hopper, lower on Blackwell (vLLM blog "State of FP8 KV-Cache," Apr 22, 2026). Your requests (few-shot prefix + image ≈ 3–8K tokens, short JSON outputs) are prefill-heavy, so expect modest latency gain but **more KV headroom → higher max_num_seqs → more images/hour**. Start uncalibrated; calibrate scales with llm-compressor only if eval dips persist (uncalibrated is worst case; typically 1–2 pt max degradation).
7. **AWQ/GPTQ INT4 (W4A16)** — for fitting 32B-dense on one 5090 or maximizing batch. VLM caveat: INT4 is *usually* near-lossless (AWQ ≈ FP16 on MME for Qwen-VL) but has model-specific blowups (AWQ lost >10 pts on LLaVA-OneVision-72B; MBQ/VLMQ papers show LLM-centric calibration ignores visual tokens — arXiv 2412.19509, 2508.03351). Also instance-level divergence: aggregate benchmarks can hide per-image flips ("Does Acceleration Cause Hidden Instability in VLMs," arXiv 2503.06794) — evaluate on *your* defect eval set, per class, not just MME.
8. **NVFP4** — highest ceiling on paper (~2–2.3x over FP8 decode, near-FP8 accuracy via 16-elem blocks + FP8 scales; 88% lower quant error than MXFP4 — NVIDIA/Medium NVFP4 analyses, Jul 2026; Spheron NVFP4-vs-MXFP4 guide 2026), **but SM120 consumer-Blackwell support in vLLM/FlashInfer is still maturing**: missing MoE-kernel arch checks, illegal-instruction and CUDA-graph crashes reported into 2026 (vLLM #31085/#33416/#35065, FlashInfer #2577, HF nvidia NVFP4 model discussion). Timebox it; treat as an experiment, expect build pinning + `FLASHINFER_CUDA_ARCH_LIST=12.0f`-style workarounds.

**Phase 3 — Decode acceleration (weeks 3–4).**
9. **Speculative decoding — works for Qwen3-VL in vLLM (2026):** **AngelSlim publishes EAGLE-3 draft models for Qwen3-VL 2B/4B/8B/30B-A3B**, benchmarked on vLLM v0.12.0 across multimodal tasks: accept length 1.8–3.5, **1.4–1.9x speedup** at num_speculative_tokens 2–4 (HF AngelSlim/Qwen3-VL-*_eagle3 cards; vLLM Speculators v0.3.0 blog, Dec 2025). MTP is target-model-dependent (built into some 2026 multimodal checkpoints, e.g., Qwen3.6-27B recipe). Caveat: your outputs are short constrained JSON (~200–500 tokens) and batch throughput is compute-bound at high concurrency, where spec-decode gains shrink — this helps the interactive QA mode most. Verify spec-decode + structured-outputs interaction on your pinned vLLM version.
10. **Vision-encoder cost profiling / disaggregation** — vision encoding is compute-bound, decode memory-bound; encoder work serializes batches when co-located (vLLM Encoder-Disaggregation blog, Dec 15, 2025: 2–2.5x goodput for multi-image requests with EPD, available ≥ v0.11.1). With 3–5 crops per frame you're in exactly the multi-image regime EPD targets. Cheaper first step: profile encoder-vs-LLM time (encoder tokens ≈ pixels/1024 at ~4x pre-merge compute); if encoder-bound, dedicate 1 of 4 GPUs as encoder tier (5090s excel at compute-bound ViT work — arXiv 2603.12707 cross-tier GPU heterogeneity study, 2026).

**Phase 4 — Combine + lock.** Best combo candidate for this workload: **FP8 weights + FP8 KV + panel crops at tuned max_pixels + shared few-shot prefix (cached) + 4-way DP + tuned max_num_seqs**, with EAGLE-3 enabled for the interactive endpoint only. Re-run the full frozen eval + κ vs human; freeze `{model, quant, prompt_sha, schema, engine version}` as the release artifact.
