# LLM Serving Optimizations for vLLM ≥0.17 on 4x RTX 5090 (SM120, PCIe-only) — mid-2026 status

Context anchors: vLLM mainline is at ~v0.22 as of July 2026 (EAGLE 3.1 blog, vllm.ai, 2026-05-26 says "upcoming v0.22.0"); v0.17.0 bumped to PyTorch 2.10 and shipped a dedicated **SM120 FP8 GEMM optimization** (vLLM v0.17.0 release notes, newreleases.io). Workload = long vision prefill (1K–9.4K tokens/img) + shared few-shot prefix + short (~200–500 tok) constrained-JSON decode → **prefill-dominated, prefix-cache-friendly, decode cost small**. Optimizations that shorten/parallelize prefill and dedupe the shared prefix dominate; decode-side tricks (spec decode) are second-order.

## 1. Quantization ladder on SM120

| Scheme | SM120 status (mid-2026) | Verdict |
|---|---|---|
| **FP8 W8A8** | Native FP8 tensor cores; CUTLASS w8a8 FP8 for SM120 merged (vLLM PR #17280) and v0.17.0 added dedicated SM120 FP8 GEMM path (release notes). Dynamic per-token activation quant is the default llm-compressor recipe (`FP8_DYNAMIC`), no calibration needed; static (calibrated) activation scales shave a little more per-token overhead. FlashInfer kernel path used for FP8 linears on Blackwell (vLLM issue #21648). | **Mature — default choice.** ~2x weight memory saving, prefill compute speedup, near-lossless. |
| **INT8 W8A8 / SmoothQuant** | **Explicitly unsupported on Blackwell**: vLLM docs (llm-compressor INT8 W8A8 page) state INT8 is supported on CC 7.5–<10.0 and say "use FP8 instead" on Blackwell. | **Dead on SM120. Skip.** |
| **AWQ/GPTQ W4A16** | Runs via **Marlin** (`gptq_marlin` / `awq_marlin`) — portable, works on SM120. Community bench (zenn.dev, vLLM 0.11, RTX 5090): GPTQ-Marlin 8–19% faster than AWQ-Marlin; Qwen3.5-35B-A3B-GPTQ-Int4 ~195 tok/s on one 5090 (HF discussion, 2026). **Machete does NOT support SM100/120** (Hopper wgmma-only, vLLM issue #35439). | **Mature (Marlin path).** Best when VRAM-bound; W4A16 decode is fast but prefill is dequant-bound — for your prefill-heavy workload FP8 usually wins throughput. |
| **W4A8** | CUTLASS W4A8 kernel is CC 90 only; Machete no SM100+ (issue #35439). llm-compressor AutoRound W4A8 on 2026 roadmap, not landed. | **Not available on SM120. Skip.** |
| **NVFP4** | Works on SM120: dense NVFP4 checkpoints load directly; MoE needs `VLLM_USE_FLASHINFER_MOE_FP4=1`; **FlashInfer b12x MoE + FP4 GEMM kernels for SM120/121 merged 2026-05-20** (vLLM PR #40082): `VLLM_NVFP4_GEMM_BACKEND=flashinfer-b12x`, `--moe-backend=flashinfer_b12x`. Gaps remain for some native NVFP4 MoE kernels (issue #31085). Community repos exist specifically for Qwen3.5 NVFP4 on SM120 (github aliez-ren/vllm-qwen3.5-nvfp4-sm120). | **Works, maturing fast.** Use for the 122B MoE if FP8 doesn't fit; expect occasional kernel-selection friction on consumer Blackwell (elevata.io report: "configure SM120 explicitly"). |
| **MXFP4** | Triton MXFP4 backend enabled on SM120 (vLLM PR #31089); FlashInfer MXFP4 MoE for SM120 tracked in flashinfer #2847. Same FP4 tensor-core HW as NVFP4; pick MXFP4 only for checkpoint availability (gpt-oss style) — NVFP4 has finer scaling (Spheron NVFP4-vs-MXFP4 guide, 2026). | **Works (Triton path).** |
| **GGUF** | Moved to out-of-tree `vllm-gguf-plugin`; docs still say "highly experimental and under-optimized"; slow TTFT reports persist (issue #35987). | **Skip.** |
| **KV cache quant** | `--kv-cache-dtype fp8` (e4m3) is the 2026 recommendation; e5m2 legacy. vLLM blog "State of FP8 KV-Cache" (2026-04-22): ITL slope ~54% of BF16, break-even ~4–7k context, 93–98% long-context AUC recovery *uncalibrated*, ≤1–2 pt on reasoning; calibrate via llm-compressor only if drops persist. New flags: `--kv-cache-dtype-skip-layers sliding_window`, per-head scales. INT8 KV **not** supported. Blackwell path = FlashInfer. Caveat: head_dim=256 models see ~1.6x **prefill regression** — check your VLM's head_dim before enabling; with 9.4K-token images + shared prefix, FP8 KV doubles effective prefix-cache capacity. | **Mature; enable after an accuracy spot-check.** |
| **llm-compressor / AutoRound** | llm-compressor is the canonical workflow (FP8_DYNAMIC, INT8 GPTQ+SmoothQuant, NVFP4, KV scales). AutoRound integrated into llm-compressor (Red Hat/vLLM blog, 2025-12-09) supporting wNa16, FP8, MXFP8/4, NVFP4; Q1-2026 roadmap adds more schemes (llm-compressor issue #2324). Use AutoRound for best-accuracy W4A16/NVFP4 of the big MoE. | **Mature.** |
| **2:4 sparsity** | vLLM's sparse 2:4 FP8 CUTLASS path is Hopper-era; no SM120 enablement found anywhere in vLLM/SGLang for consumer Blackwell in 2026; only research kernels. Also requires a pruned checkpoint (none for Qwen3-VL/GLM-4.6V). | **Not practical on SM120. Skip.** |

## 2. Attention / kernel level

- **Attention backend on SM120**: FlashInfer works (`--attention-backend flashinfer` widely used on 5090), **but** the fast trtllm-gen FMHA cubins are NOT compiled for SM120/121 (TensorRT-LLM issue #11799; flashinfer #2555 — SM120 kernels exist but unwired, need `ENABLE_SM120` build). So SM120 FlashInfer/FA fall back to FA2-class kernels; FA3 is Hopper-only. Practical: benchmark `FLASH_ATTN` vs `FLASHINFER` vs `TRITON_ATTN` on your model — differences of 5–15% are commonly reported; FlashInfer usually wins decode, FA prefill. v0.17 added FlashAttention 4 integration (release notes) — check if FA4 covers SM120 in your build.
- **CUDA graphs**: V1 default is `FULL_AND_PIECEWISE`-style capture; modes `PIECEWISE` / `FULL` / `FULL_DECODE_ONLY` / `FULL_AND_PIECEWISE` via `--compilation-config '{"cudagraph_mode": "..."}'` (vLLM cuda_graphs design doc). **Full CUDA graphs confirmed working on sm_120** — community reported 8x over enforce-eager on a 5090 (vLLM issue #37242, WSL2; native Linux better). Never run `--enforce-eager` in production; for short-decode workloads CUDA graphs are one of the biggest decode wins. `FULL_DECODE_ONLY` is a good fit for your uniform short decodes if `FULL_AND_PIECEWISE` capture fails with FlashInfer.
- **torch.compile**: `VLLM_COMPILE` backend default; `-O0..-O3` flag (O2 default, O3 aggressive); `use_inductor_graph_partition=True` experimental with torch≥2.9 (vLLM compilation docs/DeepWiki). Compile artifacts cached under `VLLM_CACHE_ROOT` → subsequent startups fast; pre-warm once per config. For nightly batch jobs, `-O3` is free money since startup amortizes over thousands of frames.
- **Chunked prefill**: on by default in V1. Key knobs: `--max-num-batched-tokens` (throughput: ≥8192; with 9.4K-token images consider 16384–32768 so one image prefills in ~1 chunk), `--long-prefill-token-threshold`, `--max-num-partial-prefills`. VLM-specific: `--disable-chunked-mm-input` keeps an image's embedding chunk intact (avoids splitting one image across steps).

## 3. Scheduling / batching

- `--max-num-batched-tokens`: for pure batch throughput set high (16–32K); for the interactive endpoint keep ~2–8K to protect ITL (vLLM optimization docs).
- `--max-num-seqs`: raise until KV-bound; with short outputs, decode batches drain fast — larger values keep decode batches full.
- **Priority scheduling**: `--scheduling-policy priority` + per-request `priority` (lower = earlier). Lets you co-host batch + interactive on one engine (interactive priority 0, batch 100); with chunked prefill decode is already favored. Mature.
- **Async scheduling** (`--async-scheduling`): overlaps CPU scheduling with GPU step; became a headline feature/default around v0.14 (Medium, vLLM v0.14 writeup). With very short outputs, per-step CPU overhead matters — verify it's on.
- **Offline vs server**: `LLM.generate`/`LLM.chat` avoids HTTP/SSE/tokenizer-process overhead and is the right tool for the thousands-of-frames batch run; if you must use the server, `--api-server-count N` parallelizes tokenization+media decode, `VLLM_MEDIA_LOADING_THREAD_COUNT` (default 8/server), `VLLM_USE_FASTOKENS=1` (Rust tokenizer) — all in current optimization docs.
- **Parallel sampling (n>1)**: V1 fans out to n child requests + a `max_tokens=1` warmup to populate prefix cache, so the shared prompt KV is computed once and shared via block ref-counting (PR #13421, prefix-caching design doc). Cheap if you want self-consistency voting on inspection verdicts.
- **Multimodal caches**: `mm_processor_cache_gb` (default 4 GB; type `shm` for TP>1) dedupes identical images/preprocessing across requests; `--mm-encoder-tp-mode data` runs the ViT data-parallel across TP ranks — significant for 4464x2160 frames since the encoder is otherwise replicated work on TP=4. High-value for your workload.

## 4. Caching

- **Prefix caching**: default-on; block-hash (sha256 default since v0.11) with LRU eviction; hashes include mm-input hashes so identical images also hit (prefix-caching design doc). Your shared few-shot prefix (text + exemplar images) will hit after the first request — order the batch so frames sharing exemplars are contiguous, and keep the prefix byte-identical (same image bytes, same sampling of few-shot).
- **Cache salting**: `cache_salt` request field isolates cache between tenants (RFC #16016, PR #17045). Use one salt per run if you want deterministic cache scoping; otherwise ignore.
- **KV offloading**: now **native** — `--kv-offloading-backend native --kv-offloading-size <GB>` (OffloadingConnector; vLLM blog 2026-01-08 + KV Offloading Usage Guide). Async DMA to CPU, promoted back on hit; multi-tier (NVMe/remote) RFC #38260 in progress. With 225 GB NUMA-local RAM this is the cheapest way to make the interactive QA endpoint's long, diverse contexts survive eviction. **LMCache** adds disk persistence across restarts + 3–10x TTFT reduction on reuse (LMCache docs); prefer native connector first, LMCache if you need persistence/NVMe.
- **Prefix-aware routing across replicas**: if you run 4x DP replicas (one per GPU) instead of TP=4, use the Rust **vLLM Router** (vLLM blog 2025-12-13; consistent-hash / prefix-aware policies) or production-stack prefix-aware routing so frames land where their few-shot prefix is cached. vLLM's built-in `--data-parallel-size` LB is not prefix-aware. For an offline batch you can trivially shard the frame list yourself — do that instead.

## 5. P/D disaggregation (single node, 4 GPUs)

Supported and demonstrated on a single node — vLLM blog "Next-Level Inference: single-node P/D" (2026-04-07, MORI-IO connector) showed 2.5x goodput on 8x MI300X, and process-level single-GPU P/D is an open RFC (#27093). **But**: the win comes from isolating decode ITL from prefill interference under mixed latency SLOs, and transfers assume RDMA/NIXL-class paths. On a no-P2P PCIe consumer box the KV transfer runs over host memory, and your workload has ~10–40:1 prefill:decode token ratio with *no* strict ITL SLO on the batch side. Chunked prefill already gives you the same effect in-engine. **Verdict: not worth it for you.** The better "disaggregation" is coarse: dedicate N GPUs to the batch engine and 4−N (or a small-model replica) to interactive QA.

## 6. Speculative decoding

- **ngram / prompt-lookup**: native (`speculative_config={"method":"ngram",...}`). Excellent fit for constrained JSON — keys/boilerplate repeat verbatim across frames, so acceptance on structural tokens is high, and it's model-free/free to try. Caveat: gains shrink at high batch occupancy (compute-bound decode) — and one 5090 report saw minimal single-user gains with low acceptance (issue #37242); measure.
- **Suffix decoding**: now a first-class vLLM method (`{"method":"suffix","num_speculative_tokens":16-32}`), requires `pip install arctic-inference` (vLLM docs; Snowflake blog). Matches against prompt **and previous generations** with frequency stats — for thousands of near-identical JSON outputs this should beat ngram (Snowflake: 1.4–3.9x over prompt-lookup). **Top candidate for your decode side.**
- **EAGLE3**: fastest learned method; EAGLE 3.1 merged for v0.22 with 1.66–2.03x (vLLM blog 2026-05-26); needs a trained draft head — availability for Qwen3-VL/GLM-4.6V text stacks is spotty; multimodal EAGLE support exists but is per-model. Only worth it for the interactive endpoint.
- **Medusa**: still in tree, superseded by EAGLE3 — skip. **Draft-model**: V1 support lagged V0 for a long time; ngram/EAGLE/suffix are the maintained paths.
- **Structured-output interaction**: spec decode + structured outputs works with both xgrammar and guidance since PR #14702 (grammar validates draft tokens; rejected drafts are just wasted compute, no correctness risk). With ~300-token outputs and high JSON regularity, spec decode is real but bounded — decode is maybe 20–30% of your E2E time; expect single-digit-to-~20% E2E gains.

## 7. Output side

- **xgrammar** is the default structured-output backend and the fastest in 2026 (SqueezeBits guided-decoding bench; xgrammar paper); schema compiles once (20–50 ms) and is cached — reuse ONE schema object for the whole run. Guided decoding still costs throughput at high batch — benchmark with/without at your batch size.
- Schema design: short keys, `enum`s instead of free strings, `"additionalProperties": false`, no `pattern` on long strings (regex → larger grammar), integers over floats. 200→120 tokens/output is a direct 1.7x decode saving.
- Set tight `max_tokens` (guards runaway), `stop` on the closing brace is unnecessary with grammar-terminated JSON but harmless. Non-streaming for batch (skips SSE chunk overhead); streaming only for the QA endpoint.

## 8. System level

- **NUMA**: vLLM now has first-class `--numa-bind` / `--numa-bind-nodes` / `--numa-bind-cpus` (optimization docs). On a multi-die/2-socket box, bind each engine's workers + your image-decode dataloader to the GPU-local node; effect is mostly on H2D of image tensors and preprocessing, 5–15% typical. Reserve ≥ 2 + N_GPU physical cores per instance (docs).
- **PCIe/H2D**: vLLM uses pinned buffers internally; your lever is decode-side — send pre-resized JPEGs (client-side downscale to your max_pixels) so media decode + H2D shrinks; raise `VLLM_MEDIA_LOADING_THREAD_COUNT`.
- **No P2P**: with P2P disabled, vLLM's custom allreduce is off → TP=4 allreduce goes NCCL-through-host. This makes **TP=4 tax real**; prefer TP=2+DPx2 or DPx4 with small models, TP=4 only when the model doesn't fit otherwise (community: informatico-madrid/blackwell-linux-infra-optimizer repo documents SM120 P2P deadlock workarounds — `NCCL_P2P_DISABLE=1` explicitly).
- **Power limit**: no clean public 5090 curve; 4090 data (dev.to Maxim Saplin) shows ~82% perf at 50% power and a knee around 70–80%; decode is bandwidth-bound so a 575→450 W cap typically costs little on decode but more on prefill (compute-bound) — your workload is prefill-heavy, so sweep 450/500/575 W with `nvidia-smi -pl` on a real batch. 4 cards at 575 W = 2.3 kW sustained; capping to ~450 W each is usually the right thermal/perf tradeoff.
- **MPS**: works for packing multiple vLLM processes per GPU but each engine pre-allocates KV, so it only makes sense for small models (e.g., Qwen3-VL-8B batch replica + tiny QA model on one card with split `gpu_memory_utilization`). No isolation; MIG unavailable on consumer cards. Marginal for you.

## 9. Notable extras a 2026 playbook adds

- **`--enable-expert-parallel`** for the MoE candidates (A3B/A10B): EP over TP for expert layers reduces the PCIe allreduce burden; EPLB (expert load balancing, async rebalance in 0.17) matters at larger scale.
- **Sleep mode** (`sleep`/`wake` levels, incl. new level-0 enqueue/wait in 0.17): swap the big batch model out of VRAM to host RAM between runs so the interactive endpoint can own the GPUs off-hours.
- **Compile/warmup hygiene**: persist `VLLM_CACHE_ROOT`, warm one request per (schema, image-size bucket) before timing.
- **`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`** — repeatedly cited in SM120 configs to avoid fragmentation OOM (issue #37242).
- **Bucketing image sizes** (fixed max_pixels → uniform vision token count) stabilizes CUDA-graph shapes and batch packing.
- **vllm bench serve/throughput** built-in harness for A/B-ing every knob above; InferenceMAX-style sweeps (vLLM blog 2025-10-09) are the model to copy.

**Priority order for your workload**: FP8 W8A8 (or NVFP4 for 122B MoE) → prefix caching + batch ordering by shared prefix → `mm-encoder-tp-mode data` + mm processor cache → max_num_batched_tokens 16–32K → full CUDA graphs (`FULL_DECODE_ONLY` fallback) + `-O3` → FP8 KV cache (after accuracy check) → suffix/ngram spec decode → native CPU KV offload for the QA endpoint → power-limit sweep. Skip: INT8, W4A8, 2:4 sparsity, GGUF, single-node P/D, MPS.
