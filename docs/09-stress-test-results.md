## 1. 결론 네 줄

1. **처리량 상한은 약 720 출력 tok/s** (혼합 워크로드, DP=2). 포화점은 동시 16이며 그 이상은 지연만 늘어난다
2. **권고 동시성 11** (포화점 16의 70퍼센트). 지연 요건이 빡빡하면 더 낮춰야 한다
3. **DP=2 확장 효율 1.95배.** 거의 선형이며 레플리카 추가가 그대로 처리량이 된다
4. **병목은 KV 캐시가 아니라 `--max-num-seqs` 다.** KV는 최대 64퍼센트만 찼고 preemption은 한 번도 없었다

## 3. 파괴점: 동시 64에서도 실패 0퍼센트

전 구간 실패율 0이다. TTFT p95가 20초, 전체 p95가 32초로 클라이언트 타임아웃(TTFT 60초, 전체 300초)에 닿지 않았다. LB 5xx도 없었다.

즉 이 구성의 파괴점은 64보다 위이며, 실무 상한은 에러가 아니라 **지연 요건이 결정한다.**

| 지연 요건 | 감당 가능한 동시성 |
|---|---|
| TTFT p95 5초 이내 | 4 |
| TTFT p95 7초 이내 | 8 |
| TTFT p95 10초 이내 | 16에서 24 |
| 지연 무관, 처리량만 | 48 |

## 4. DP=2 확장 효율 1.95배

같은 워크로드를 레플리카 1개(`:8001` 직결)에만 걸어 비교했다.

| | 최대 처리량 | 포화점 | 포화점 TTFT p50 |
|---|---|---|---|
| 레플리카 1개 | 370 tok/s | 12 | 1.8초 |
| **DP=2 (LB)** | **720 tok/s** | 16 | 2.1초 |

**1.95배.** P2P가 막힌 GeForce 박스에서 레플리카 방식을 고른 판단([04 3번](04-gpu-pinning-and-serving.md#3-서빙-토폴로지-tp-vs-pp-vs-dp))이 실측으로 확인됐다. 처리량이 부족하면 GPU 2-3에 레플리카를 추가하는 것이 가장 확실한 수단이다. 단 RAM 몫 제약이 있다([04 1번](04-gpu-pinning-and-serving.md#1-공용-모델-첫-가동-절차)).

LB 분배는 zone 수정 이후 균등하다. 이 수정 전이었다면 DP=2 효율은 1.0에 가까웠을 것이다.

## 5. 해상도가 처리량을 지배한다

시나리오를 하나씩 단독으로 돌린 결과다(동시 16, LB 경유).

| 시나리오 | 이미지 토큰 | 출력 tok/s | TTFT p50 | 전체 p95 |
|---|---|---|---|---|
| S1 텍스트만 | 0 | **1885** | 0.16초 | 2.2초 |
| S2 1MP (1024x1024) | 약 1.0K | **1614** | 0.37초 | 2.6초 |
| S3 native (4464x2160) | 약 9.4K | **206** | 9.2초 | 16초 |

- native 이미지는 텍스트 대비 **처리량 1/9, TTFT 57배**다
- 1MP는 텍스트 대비 처리량 86퍼센트를 유지한다. **1MP까지는 사실상 공짜다**
- 혼합 워크로드에서 native가 30퍼센트만 섞였는데 전체 처리량이 657 tok/s로, 텍스트 전용의 35퍼센트까지 떨어졌다

**해상도 사다리([06 해상도 사다리](06-inspection-agent-design.md#해상도-사다리), [07 Phase 1](07-inference-optimization-roadmap.md))가 최우선 최적화라는 것이 수치로 확인됐다.** 전처리에서 패널 크롭으로 1MP 부근을 맞출 수 있으면 처리량이 8배 가까이 오른다.

## 6. 병목은 KV가 아니라 max-num-seqs

기동 로그의 "최대 동시성 8.26x"는 32K 컨텍스트를 꽉 채운 요청 기준이다. 실제 요청은 1K에서 10K 토큰이므로 KV는 여유가 있었다.

| 지표 | 실측 | 판정 |
|---|---|---|
| `kv_cache_usage_perc` 최대 | **64퍼센트** | KV는 남았다 |
| `num_preemptions_total` | **0** (전 구간) | KV 압박 없음 |
| `num_requests_running` 최대 | **30.4** | `--max-num-seqs 16` × 2 = 32 상한에 닿았다 |
| `num_requests_waiting` | 동시 48부터 14, 64에서 30 | 초과분은 전부 큐 대기 |

따라서 **다음 최적화 1순위는 `--max-num-seqs` 상향(16에서 24 또는 32)이다.** KV에 여유가 있으므로 `--gpu-memory-utilization` 0.965 상향([08 8번](08-optimization-catalog.md#8-플래그-스택-실측-확정))보다 먼저 시도할 값이다. Mamba cache 블록 한계([02 Hybrid 주의](02-model-candidates.md))가 실제로 어디서 걸리는지도 이 실험에서 같이 확인된다.

## 7. 타 팀 무침범 증빙

부하기는 GPU를 요청하지 않았고 cpuset은 `12-15,44-47`(dst+dmt 배정의 부분집합), NUMA 구역 0, RAM 상한 8g였다. 감시 프로세스가 1초 간격으로 타 팀 GPU와 서버 지표를 기록했다.

| 항목 | 5개 런 최악값 | 임계 | 판정 |
|---|---|---|---|
| 타 팀 GPU(4-7) 최고 온도 | 65도 | 83도 | 여유 18도 |
| 우리 GPU(0-1) 최고 온도 | 75도 | 참고용 | 정상 |
| 우리 GPU(0-1) 최고 전력 | 468W | 450W 캡 | 캡 동작 중 |
| load average 최대 | 17.5 | 96 | 여유 큼 |
| MemAvailable 최소 | 432 GB | 20 GB | 여유 큼 |
| 우리 컨테이너 메모리 최대 | 19.6 GiB | 몫 225 GiB | 여유 큼 |
| 부하기 컨테이너 CPU 최대 | 9퍼센트 | 참고용 | 측정 오염 미미 |

가드는 한 번도 발동하지 않았다. 타 팀 GPU의 SM 클럭 하락도 없었다(busy 표본 기준).

GPU 2-3은 전 구간 유휴로 유지했고, 타 팀 GPU와 포트에는 접근하지 않았다.

## 8. 한계

- 측정 중 타 팀의 `--cpuset-cpus` 없는 컨테이너가 우리 코어에 스케줄될 수 있었다([05 도커 사용 시](05-strad32-team-resource-split.md#도커-사용-시)). load average는 12에서 17.5 범위였고 우리 GPU util이 96퍼센트 이상이었으므로 GPU 바운드 구간의 수치는 영향이 작다. 다만 절대값은 이 조건에서의 실측이다
- 부하기 cpuset이 서빙 컨테이너 cpuset과 겹친다. 부하기 CPU 사용률이 9퍼센트 이하였으므로 영향은 작다
- 이미지는 합성이다. vision 토큰 수는 픽셀 수로 동일하지만 JPEG 크기가 실 프레임보다 작아 HTTP 본문 파싱 비용이 조금 덜 든다
- `run2`(레플리카 직결) 중 dst 트래픽이 섞였을 수 있다. `engine.csv`의 요청 수 증분으로 확인 가능하다
- 출력 길이를 256으로 고정했다. 실제 inspection 응답이 더 길면 처리량은 그만큼 내려간다
